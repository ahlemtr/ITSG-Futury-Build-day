## 1. What the platform is now

An EEL test platform that replaces eVpT for income replacement benefits, with two views in one React app:

- **ITSG view:** Overview, Spec-Änderungen (upload a new spec version), Testkatalog, Einreichungen, Klärungsfälle (advisor queue), Prüfberichte (signed reports), Wissensgraph.
- **Vendor view** (switch in the top bar, "Hersteller"): the vendor's test runs round by round (story, upload of TEEL0, receipt, rule check, insurer reply TEEK0 to download and import), results, reports. Upload stands in for the GKV communication server.

**Core idea:** every time a new rule drops (a Verfahrensbeschreibung, the Gemeinsame Grundsätze, a Rundschreiben of the insurers), it is uploaded, chunked, embedded, diffed against the previous version, analysed by the AI, and the knowledge graph and the test catalogue grow. The more the graph holds, the better retrieval finds the passages, rules and test cases a change touches.

**Starting point** (`SPEC_BASELINE=VB@13.3`): the platform knows VB 13.3 and the other documents (GG 13.1, Beispielpapier, Pool-Testaufgaben, Rundschreiben Anl. 1 to 3, Hinweise, ITSG criteria) and one test case, **Peter** from the Hinweise document (step 1 = ITSG's real TEEL0 file, steps 2 to 7 generated by the rules engine). No submissions. VB 13.4 arrives through the upload.

## 2. How to run (Windows, this machine)

Prerequisites: Docker Desktop running, `uv`, Node 24, `pdftotext` (Git for Windows). `.env` (not committed) holds `OPENAI_API_KEY`, `OPENAI_MODEL`, `DATABASE_URL=postgresql://eel:eel@localhost:5432/eel`, `KG_BACKEND=graph`, `NEO4J_URI=bolt://localhost:7687`, `NEO4J_PASSWORD=changeme`.

```
docker compose up -d postgres neo4j

# reset to the starting point (stop the API first)
SPEC_BASELINE=VB@13.3 uv run python -m tools.reset_baseline              # Postgres: Peter only, no submissions; uploaded versions removed
SPEC_BASELINE=VB@13.3 uv run python -m kg.build --skip-extract --fresh   # Neo4j: baseline graph with chunks and embeddings

# servers
SPEC_BASELINE=VB@13.3 SEED_ON_START=0 uv run uvicorn api.main:app --port 8000
cd ui && npm run dev                                                       # http://127.0.0.1:5173, proxies /api to :8000

# checks
uv run pytest -q          # 174 passed, 27 skipped; graph tests write to Neo4j, run them only with NEO4J_TESTS=1 on a full graph
uv run ruff check .
cd ui && npm run build && npm run check:i18n

python -m tools.make_vendor_uploads   # sample vendor files in samples/vendor_uploads/ (gitignored: round 1 is ITSG's file)
```

Notes: `uvicorn --reload` hangs on Windows (the old worker keeps serving), restart by hand. The machine runs low on memory with Docker + API + Vite; Claude Code then kills background servers. LLM answers are cached in `data/llm_cache/` by a hash of the prompt, so the same upload twice returns instantly (that is why a second 13.4 upload shows no real AI time; delete the cache to see it again). Embeddings are cached in `kg/build/embeddings.jsonl`.

## 3. Architecture

| Layer | Where | Notes |
|---|---|---|
| UI | `ui/src/` | React + Vite, `data/api.ts` = all backend calls and mapping to `data/types.ts`; stores `advisorStore.ts`, `runStore.ts`, `aiActivity.ts` (AI overlay); `runTexts.ts` = hand-written vendor run texts; i18n DE default, EN on a button (`i18n/*.json`, legal terms stay German) |
| API | `api/main.py`, `api/routes/*` | FastAPI; `specs.py` (spec upload, jobs), `kgview.py` (graph tab), `overview.py`, `checking.py`, `runs.py`, `builder.py`, `catalogue.py`, `criteria.py` |
| Engine | `engine/` | parser/writer, rules (Vorerkrankung, EFZ, formats), expected chains, checker, runs, builder, spec diff, report + Ed25519 signing. Calculations never come from the LLM |
| Knowledge graph | `kg/` | seed files `kg/seed/*`, extraction `kg/extract/*`, `seed_graph.py` (build, baseline filter, overlays), `yaml_backend.py` / `graph_backend.py`, `chunks.py`, `embed.py`, `load.py`, `ingest.py` (upload pipeline) |
| LLM | `llm/` | OpenAI Structured Outputs; agents in `llm/agents/` (`change_analysis`, `calculation_analysis`, `spec_update`, `check`); the model only answers, code validates (citations must be real passage keys, parameter names and types checked) and writes; API errors degrade to "no answer" |
| Store | `store/` | `PgRepo` (Postgres) and `MemoryRepo` with the same methods; schema `store/schema.sql` |

**Neo4j holds the knowledge:** documents and versions, passages and chunks (full-text + vector index), changes, rules, parameters per version, layouts, test-case definitions, precedents. **Postgres holds the operations:** submissions and checks, runs, reports, test status and approvals, upload jobs (`ingest_job`), growth log (`kg_event`). Files on disk under `data/`.

**Upload pipeline** (`kg/ingest.py`, `POST /spec-versions`, background thread, `GET /jobs/{id}`): store → chunk → embed → diff → map (changes → passages → rules) → AI analysis → apply → catalogue. What it learns is written as an overlay folder `data/ingested/<doc>@<version>/` (document, passages, diff, curated changes, parameter values, expected results, new tests, calculation rules) that the seed build loads on top of the baseline; Neo4j gets it through the normal load. Valid-from in the future = next year's catalogue in parallel; valid now = open submissions re-checked. Rundschreiben: calculation rules become draft rules `CALC-<doc>-<n>` (never used in checks), values for engine parameters become proposals for ITSG.

## 7. Decisions taken while building (check with the team)

1. The fake KB of decision D1 is gone: tests run on the KG's YAML backend. The engine keeps its own typed test case `Case` (`Case.from_kb` / `to_kb`, loaded with `engine.expected.get_case`); the KG's `TestCase` has dict inputs.
2. `engine/model.py`: the KG contract part is the KG teammate's file; the engine models are appended below it. `engine/layouts.py` derives the repeating group, the DSLW block order and the MM flag per block from the flat KG layouts.
3. Only repeating-group field names drop their `-nn` suffix (`BEGINN-AU-{nn}` -> `BEGINN-AU`). Fixed names such as `DBAP.FIRMA-1` keep it.
4. `an` values are right-stripped only, so the writer reproduces the file exactly.
5. Date fields longer than 8 characters (`DATUM-ERSTELLUNG`) stay strings.
6. `kg/seed/compare_modes.yaml`: `DBSD.DATENSATZ-ID-URSPRUNGSMELDUNG` (C-3) and `DBSD.AKTENZEICHEN-VERURSACHER` (C-2) are `rule` fields.
7. `s-three-periods` drops a middle period, `s-missing-july` the oldest. A missing oldest chained period = bug R41-3; any other missing period = correct variant.
8. `s-wrong-order` is labeled bug F41-8 as plan/02 section 7 says; order is checked by the re-check.
9. A missing 41 is a bug of the rule closest to its boundary (`deciding_rule`).
10. Peter's chain extras are in `fixtures/scenarios/peter.yaml` (ITSG file values, Hinweise IDs; derived: insurer DSIDs, KZ-AU 3, 01 salary values, 62 EEL-ABAG/ABSV, KORR-ABGABEGRUND 01 on the 88).
11. Diff matching of messages of the same type: vendor order, unless another pairing gives fewer deviations.
12. Store: `PgRepo` (when `DATABASE_URL` is set; now verified on Postgres) and `MemoryRepo` with the same methods; documents stored whole in `jsonb`.
13. Generated files copy the envelope (VOSZ, DSKO, NCSZ) of the ITSG file; the envelope is not graded.
14. Single-step test packages also carry the insurer's 61 reply.
15. Test runs: round N grades the employer messages of round N; the reply is the expected insurer message adapted to the vendor's file. Every accepted round upload is also a submission `run-<id>-r<n>` (all files so far, checked only up to the steps reached), so ITSG sees it live; rejected files do not use up the round.
16. LLM: every call degrades to "no answer" without key and cache; citations must resolve in the KB; an AI proposal leaves the label `unclear` until the advisor decides.
17. Criteria pipeline: matched drafts by approved rule id and parameters compared by code; only unmatched drafts go to the AI review.
18. Seed: the full seed has 18 test cases and 10 seed submissions (used by the tests); the starting point (`SPEC_BASELINE`) has Peter only and no submissions.
19. Advisor decisions are stored as KG precedents; with the API they go to `DATA_DIR/precedents.yaml` (YAML backend) or Neo4j, never into `kg/seed/precedents.yaml`.
20. Reports show the VB passage of the rule set version first, a 3.12 part before a field passage.
21. The AI never writes: agents answer in a fixed schema, code validates and writes (`kg/ingest.py`). Parameters are versioned with the Verfahrensbeschreibung; a Rundschreiben only proposes parameter values.
22. Tests made by an upload become `TestCase` nodes in the graph (overlay `tests.yaml`) and drafts in the catalogue; ITSG approval is the human gate.
