# Spec update workflow: what the platform does when a new rule drops

This is the core of the platform, not a demo add-on. Every new document (a Verfahrensbeschreibung, Gemeinsame Grundsätze, a Rundschreiben of the insurers) goes through the same pipeline: it is uploaded, chunked, embedded, diffed against the version before, the AI works out what changed in the rules, the knowledge graph grows, and the test catalogue is updated. The more documents and decisions the graph holds, the better retrieval finds the passages, rules and test cases a new change touches: the platform's context grows with every update.

State on 2026-10-27.

## 1. Starting point

The platform starts from **VB 13.3** (`SPEC_BASELINE=VB@13.3`) with one test case, **Peter** from the Hinweise document (step 1 = ITSG's real TEEL0 file, steps 2–7 generated by the rules engine). Postgres has no submissions; vendors upload. Every later version, starting with VB 13.4, arrives through this workflow.

- Graph at the start: VB 13.3, GG 13.1, Beispielpapier 13.3, Pool-Testaufgaben, Rundschreiben Anl. 1–3, Hinweise, ITSG criteria; rules, parameters (13.3 values), Peter.
- Reset to the starting point: `SPEC_BASELINE=VB@13.3 uv run python -m tools.reset_baseline` (Postgres) and `SPEC_BASELINE=VB@13.3 uv run python -m kg.build --skip-extract --fresh` (Neo4j).
- Sample vendor files: `samples/vendor_uploads/` (`python -m tools.make_vendor_uploads`).
- The full hand-curated 13.4 knowledge (`kg/seed/changes.yaml`, 13.4 parameter values) is the reference the workflow's result is tested against; it is not loaded at the start.

## 2. The workflow

```
upload ──> store ──> chunk ──> embed ──> diff ──> map ──> AI analysis ──> apply ──> catalogue
 PDF       file +    passages  vectors   against  changes   what changed    graph +    recompute,
           job       + chunks            previous to rules  in the rules    Postgres   drafts
```

| Stage | Does | Writes |
|---|---|---|
| upload | ITSG uploads the PDF on the Spec changes screen: document type, version, valid from (read from the title page when possible, e.g. "ab 01.01.2027") | file in `DATA_DIR/specs/`, job row in Postgres |
| chunk | `kg/extract` splits it into passages by section (VB: per section and part, others: per heading); long passages are split into overlapping chunks for search | passages + chunks |
| embed | OpenAI embeddings per chunk (cached) | vectors |
| diff | against the version the new one succeeds (`engine/specdiff.py`): changed, added, removed text per section and field | raw changes |
| map | each change to the passages it modifies (old and new), those passages to the rules that cite them (`SOURCED_FROM`) and through the rules to the test cases (`TARGETS`): rules to recompute, rules to review | impact |
| AI analysis | the spec-update agent reads every change that touches a rule: summary, label (editorial / clarification / law change), in scope or not, which parameter changes and its new value (e.g. `gap_inclusive` false → true), with citations. No citation, no result | curated changes, new parameter values |
| apply | the new version, its passages, chunks, changes and parameter values go into the knowledge graph (Neo4j) and Postgres; the parameters the AI did not change carry over | graph grows |
| catalogue | the rules engine computes every test case's expected result under the new version; tests whose result flips are flagged, the builder drafts boundary tests and hidden variants | drafts in the Test catalogue |

The human gate is the Test catalogue: drafts are approved by ITSG before vendors get them. Every AI step runs as a background job; the screen shows an animated stage list while it runs.

### This year or next year

The **valid-from date** decides, compared with today:

| New version valid from | Meaning | What changes |
|---|---|---|
| in the future (VB 13.4, 01.01.2027) | next year's rule set, prepared in parallel | the catalogue gets the expectations for the new version and drafts; today's checks stay on the rule set in force; on the valid-from date the platform switches by itself (`params.version_on`) |
| today or in the past (a correction of the rule set in force) | the rule set in force changes now | same, plus: open submissions are re-checked under the new version and test cases whose result flips need re-approval before the next vendor run |

### The insurers' calculation rules (Rundschreiben)

The Gemeinsame Rundschreiben of the GKV-Spitzenverband (Anl. 1: Kinderkrankengeld, Anl. 2, Anl. 3: Entgeltersatzleistungen, e.g. Regelentgelt, Berechnung, Entgeltfortzahlung) are today **retrieval only**: 378 passages, linked to no rule or parameter. In this workflow they are documents like any other:

1. A new Rundschreiben edition is uploaded with its type and date; it succeeds the previous edition.
2. Chunk, embed, diff against the previous edition.
3. The AI analysis looks for **calculation rules**: amounts, percentages, periods and thresholds (e.g. EFZ six weeks, Krankengeld 70 % of the Regelentgelt, at most 90 % of the net pay, 78 weeks), each with a citation.
4. Where a value feeds a parameter the engine already uses (e.g. the six weeks of the EFZ end, `efz_weeks`), it becomes a new parameter value like a VB change and the tests are recomputed.
5. Where it describes a calculation the engine does not implement yet (Krankengeld amount, Kinderkrankengeld), it is stored in the graph as a **calculation rule without engine implementation** (status `draft`, linked to its passages and message types) and listed in the Test catalogue as "needs implementation". The platform never invents an expected value it cannot compute.

Out of scope stays as in `plan/00`: maternity, child sick benefit and accident benefits are not computed; their rules are known to the graph, not to the engine.

### Which part goes where

Two databases with two jobs: **Neo4j holds the knowledge** (what the rules say and how everything is connected), **Postgres holds the operations** (what happened: uploads, jobs, submissions, verdicts, approvals). Files stay on disk under `DATA_DIR`, with their SHA-256 in Postgres.

| Data | Neo4j (knowledge graph) | Postgres (operations) |
|---|---|---|
| uploaded spec / Rundschreiben PDF | `Document`, `DocVersion` (version, valid from, succeeds) | `spec_upload`: file path, SHA-256, uploader, time |
| text | `Passage` (section, heading, text) and `Chunk` (text, embedding), full-text and vector index | – |
| what changed | `Change` (old / new text, summary, label) with `MODIFIES_OLD` / `MODIFIES_NEW` to passages | `ingest_job` and its stages (status, counts, timings, errors) |
| rules and calculations | `Rule`, `Parameter`, `ParamValue` per version, `Criterion`, `SOURCED_FROM` / `USES_PARAM` / `CONSTRAINS` edges | – |
| record layouts | `Record`, `Field` | – |
| test cases | the definition: inputs, expected result per version, `TARGETS` rules, `CLONE_OF` / `HIDDEN_OF` | catalogue status: draft / approved / rejected, approval history |
| vendor files and results | – | `submission`, `submission_file`, `check_result` (deviations, labels), `run`, `report` (signed) |
| advisor decisions | `Precedent` linked to the field and the passages that justify it (found again by the checker) | the decision in its submission's check result |
| growth | – | `kg_event`: what each upload or decision added (shown on the knowledge graph tab) |

Retrieval and impact run on Neo4j (vector + full-text search, path change → passage → rule → test case). Everything with a timestamp, a status or a signature lives in Postgres.

## 3. Steps

| Step | What | Done when |
|---|---|---|
| W0 result table | one tab per message, only deviations by default (done) | done |
| W1 starting point | `SPEC_BASELINE=VB@13.3`, Peter only, no submissions, sample vendor files (done) | done |
| W2 ingestion pipeline | `POST /spec-versions` (file, document, version, valid from) starts a job with the stages above; `GET /jobs/{id}` reports stage and counts; the result is written as an overlay (`DATA_DIR/ingested/<doc>@<version>/`) that both KG backends load, and pushed into Neo4j | uploading VB 13.4 yields the DBVO 3.12 change with `gap_inclusive` false → true, R41-2 / R41-3 to recompute and `peter-gap-exact` among the flips; the result matches the curated reference |
| W3 upload on the Spec changes screen | upload card (file, type, version, valid from); without a newer version the screen shows only this card | the 13.4 PDF can be uploaded from the browser |
| W4 AI activity overlay | one shared overlay for every background AI job (spec analysis, check triage, report explanation, stories): animated stage list with live counts (passages, chunks, changes, rules), the current stage highlighted, elapsed time; the screen stays usable | every AI call shows it; finishes into the result |
| W5 this year or next year | valid-from logic of section 2: future = parallel catalogue, now = re-check open submissions | a correction valid today re-checks the open submissions |
| W6 knowledge graph tab | "Wissensgraph": what it holds and how it grew (event log: 13.3 loaded, 13.4 uploaded +N passages / +M changes, precedent added), interactive graph around a rule (Cytoscape.js), "ask the graph": a question or a change in, relevant passages (with the matching sentence), rules and test cases out | after the 13.4 upload the counters and the log grow; the 3.12 change highlights change → passage → R41-2 / R41-3 → `peter-gap-exact` |
| W7 chunk-level search | chunks (about 1,000 characters, overlapping) embedded and searched with full-text + vector, results grouped per passage with the matching sentence | "Vorerkrankung 6 Monate" finds 3.12/chaining in the top 3 |
| W8 Rundschreiben | the same pipeline for Rundschreiben: calculation rules extracted with citations, parameters updated where the engine uses them, "needs implementation" otherwise | a new Rundschreiben edition shows its calculation changes and the affected parameters |
