# Checking and deviation analysis

How the rule checker compares a vendor's output with the model solution and classifies every difference. This replaces eVpT's preliminary evaluation (fachliche Vorbewertung) for EEL.

## 1. What eVpT does today

Sources: Pool-Testaufgaben 2025/2026 (sections 1, 2, 2.1 to 2.4, 5.x, 8) and the eVpT portal description.

| Stage | What it does | Automatic? |
|---|---|---|
| 1. Acceptance receipt | GKV communication server confirms the file arrived, eVpT sends a processing confirmation or error message | yes |
| 2. Core check (Kernprüfung) | format and plausibility checks, the same ones the real data acceptance points run (field check catalogue, Anlage 1 of the GG, maintained by the KoSKP committee) | yes |
| 3. Preliminary evaluation (Vollständigkeitsprüfung / fachliche Vorbewertung) | compares the files with **one model solution**, only for **selected** test tasks, outputs a deviation report with hint texts | yes |
| 4. Judging deviations | the vendor justifies, the system advisor decides: bug or allowed variant | **no, manual** |

Evidence that stage 3 compares values, not rules:

| Remark in the Pool-Testaufgaben | Shows |
|---|---|
| allowed variants "lead to deviations in the completeness check" (1, 2.4, 5.4, 5.6.2) | one answer only |
| tax data compared against the literal "Dummy-Steuernummer", "automatically a deviation" (5.15.3) | plain value comparison |
| extra files: "allowed deviations (too much data)" (5.11), missing reply file: "deviations from the model solution" (insolvency module) | file presence is compared too |
| "the solutions don't show the record contents completely" (5.20) | the solution itself is partial |
| "please discuss the deviations with your system advisor" (2.4) | judgement is manual |

The portal calls stage 3 a **"fachliche Vorbewertung"**, a *preliminary* evaluation. Our pitch: **"We turn eVpT's Vorbewertung into a real evaluation."**

## 2. Our flow

```
Vendor files vs model solution
        │
   1. Exact match on comparable fields (same as eVpT today)
        │
   ┌────┴──────────────┐
 match               mismatch
   │                   │
 EXACT MATCH         show the diff + analyze each deviation:
 (show the diff,       a. known-variant catalogue
  all identical)       b. rule re-check (rules engine)
                       c. AI triage (proposal only)
                       d. system advisor (only what is left)
                       │
                       └─ each deviation gets one label:
                          CORRECT VARIANT / BUG / INVALID / UNCLEAR
```

The model solution is the published solution for official tasks (TA 167, 168) or the expected files our writer generates for our own tests.

## 3. The diff: three levels

| Level | Question | How |
|---|---|---|
| Messages | is every expected message there, nothing extra? | count and type per step |
| Matching | which vendor message corresponds to which expected one? | by person + Abgabegrund + position in the chain, **not** by line number |
| Fields | which values differ inside each matched pair? | field by field, using the compare mode of each field (section 4) |

## 4. Compare modes and the ignore list

Derived from the Verfahrensbeschreibung V13.4, which states for each field who fills it. eVpT's own ignore list is in its user manual (not available to us): **confirm with ITSG**.

### Ignore: set by someone else, or a timestamp

| Record | Field | Why | Source |
|---|---|---|---|
| DSLW | DATUM-ERSTELLUNG | creation time, different every run | VB 3.1.5 |
| DSLW | DATUM-VERARBEITUNG | set by the data acceptance point when forwarding | VB 3.1.14 |
| DBID | AKTENZEICHEN-SV | free for the collecting agency (insurer side) | VB 3.19.1 |
| DBAL, DBAE | salary amounts of the 01 (BRUTTO, NETTO, EZ*, ...) | vendor payroll data, not defined by the scenario; dates and flags stay compared | `02` section 9 |
| DBNA | positions 065-125 | layout unknown (`starter/layouts/README.md`) | assumption |

### Rule: not compared to the solution, checked by a rule instead

| Record | Field | Why it differs | Rule | Source |
|---|---|---|---|---|
| DSLW | DATENSATZ-ID | UUID generated by the creator | valid UUID, never reused | VB 3.1.11 |
| DSLW | PRODUKT-IDENTIFIER | assigned by ITSG per certified program | equals the product under test | VB 3.1.12 |
| DSLW | MODIFIKATIONS-IDENTIFIER | product version | matches the submitted version | VB 3.1.13 |
| DSLW | ABSENDERNUMMER | creator's company number, each vendor has its own eVpT test number | equals the vendor's test number | VB 3.1.2, PTA 2 |
| DSLW | ABRECHNUNGSPROGRAMM | 1 payroll, 2 filling aid, 3 time recording | matches the product type | VB 3.1.20 |
| DBID | AKTENZEICHEN-VERURSACHER | free for the creator (e.g. personnel number) | identical across the case, echoed by the insurer | VB 3.19.2 |
| DBID | REFERENZ-ID | points to another message | equals the ID of the message answered | VB 3.19.3 |
| DBAP | all fields | sender's contact person | present when MM-ANSPRECH = J. Whether it is mandatory per Abgabegrund is in Anlage 3 of the VB (not available) | VB 3.18 (no table, **assumption**) |
| VOSZ, DSKO, NCSZ | envelope | file numbers, dates, sender | NCSZ record count matches | separate spec |

### Compare: everything else

Message types, person data, all dates and periods, flags, amounts, block structure. FEHLER-KENNZ and FEHLER-ANZAHL are compared too (an employer always sends 0).

## 5. The labels

| Label | Meaning | Example (Peter) | Decided by |
|---|---|---|---|
| **Exact match** | no deviation on compared fields, all rule fields valid | ITSG's reference file | diff |
| **Correct variant** | differs from the solution, but the rules allow it | the 41 lists 3 of 4 periods ("at least one, as many as possible") | catalogue, rules engine, or advisor after AI proposal |
| **Bug** | well-formed but wrong according to the rules | July period missing, pay end 30.03 instead of 27.03 | rules engine |
| **Invalid** | breaks the format, would already fail the core check | wrong length, letters in a numeric field, insurer-only field filled, MM flag without block | parser, format rules |
| **Unclear** | no rule or precedent covers it | DBAP missing on a 41 (MM-ANSPRECH = N) | AI proposes, advisor decides |

Result per test case: the worst label found (invalid > bug > unclear > correct variant > exact match). Every label carries: rule ID, ITSG criterion (if any), spec passage, expected and actual value.

## 6. The analysis steps

| Step | Input | Output | Notes |
|---|---|---|---|
| a. Known-variant catalogue | deviation signature (record, field, kind of difference) | correct variant, with the catalogue entry as reason | `kg/seed/variants.yaml`, seeded from variants the Pool-Testaufgaben name explicitly, plus precedents via `kg.find_precedent`. Candidate seed: MM-ANSCHRIFT J + DBAN (Beispielpapier 13.1) vs N (ITSG file), once ITSG confirms |
| b. Rule re-check | the vendor's value + scenario | correct variant / bug / invalid | deterministic: "does the vendor's file also satisfy the rules?" |
| c. AI triage | deviation + retrieved spec passages + similar precedents | proposal (likely variant / likely bug / unclear) + citation + confidence | never final; output rejected if it cites no passage |
| d. System advisor | proposal | final label + reason | stored as a **precedent** |

Precedents close the loop: the next time the same deviation signature appears, step a resolves it automatically. The advisor's daily decisions, lost in meetings today, become a reusable asset.

Pitch metric: "Of N deviations, X % resolved by catalogue and rules, Y % proposed by AI, Z % left for the advisor."

## 7. What the user sees

Per test case, a side-by-side view of model solution and vendor file, field by field:
- identical fields in gray, ignored and rule fields marked with their mode
- each deviation highlighted with its label and an expandable analysis (rule, spec passage, reasoning, AI proposal if any)
- if all is identical: the same view, all gray, labeled "exact match"
